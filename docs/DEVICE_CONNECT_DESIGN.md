# Cineo 设备绑定、手机输入与云端同步整合方案

**日期：** 2026-11-08  
**状态：** 待评审方案，尚未实现；本文的建议值不代表已确定的产品限制。  
**客户端：** Android TV（本仓库）与 Flutter 手机端（`/Users/benson/Documents/app/cineo-flutter`）。  
**关联文档：** [SYNC_DESIGN.md](./SYNC_DESIGN.md)、[DECISIONS.md](./DECISIONS.md)。

## 1. 推荐结论

采用“统一设备绑定 + 云端增量同步 + 按需实时输入”。手机和电视都主动连接一个可访问的 Cineo 后端，不要求用户安装 Tailscale，也不要求处于同一 Wi-Fi。

后端可以部署在第三方托管平台或自己的服务器上。“第三方托管”提供运行、存储和连接能力；Cineo 的绑定、授权、同步及冲突处理仍由项目实现。首版不依赖某家专用同步平台，不在协议中绑定具体供应商。

保留本地优先：后端不可用时，已有播放、搜索、收藏和站点管理继续使用本地能力。云端同步与手机输入显示各自状态，不阻断应用启动。

首版建议直接集成现有 Flutter App，扫码绑定一次，后续选择电视即可输入。网页输入不是技术前提，可作为以后无需安装 App 的临时入口。

## 2. 能力边界

| 能力 | 两端需同时在线 | 后端保存内容 |
|---|---|---|
| 手机给电视输入搜索词、地址或 Token | 是，且电视开启输入会话 | 短时转发密文，不进入持久同步库 |
| 历史、收藏、站点、共享设置同步 | 否，发送端须先成功上传 | 各实体最新密文、同步元数据与有效墓碑 |
| 设备列表、绑定与解绑 | 操作时需访问后端；配对时两端在线 | 设备公钥、授权关系、撤销状态 |
| 视频播放、下载与海报加载 | 不经过同步后端 | 不保存视频、音频、下载文件或海报二进制 |

“填入电视的 TMDB Token”和“向整个同步空间长期共享 Token”是两个独立行为。前者可单次发送，后者默认关闭，需要单独启用。

实时输入只针对 Cineo 自己允许接收的字段，不向系统或其他应用注入按键。首版不支持远程唤醒电视、后台强制弹窗或完整遥控器。

## 3. 总体结构

```text
Flutter 手机 App ───── HTTPS ───── Cineo 后端 ───── HTTPS ───── TV App
       │                         │                          │
       │                    设备授权与配对                   │
       │                    最新加密同步数据                 │
       └──── 按需 WSS ───── 临时消息路由 ───── 按需 WSS ──────┘

两端界面始终读本地数据库；本地修改通过 outbox 批量上传。
```

同一个后端提供三组接口，但逻辑与配额分开：配对与设备管理、持久同步、临时输入。一次绑定复用身份，避免用户为了同步和输入分别配对。

传输全程使用 HTTPS/WSS；同步载荷和输入文字额外端到端加密。后端仍能看到设备关系、消息时间、大小等元数据，不宣称完全隐藏元数据。

## 4. 设备身份与扫码绑定

### 4.1 身份模型

- 每台设备生成独立身份密钥，私钥存入 Android Keystore / iOS Keychain 等安全存储。
- `space_id` 表示一个同步空间；`device_id` 表示一台设备，不用本地 IP 或硬件序列号当身份。
- 每台设备取得独立、可撤销的访问凭证。服务端每次请求校验设备是否仍属于空间。
- 同步内容使用带版本号的空间数据密钥；输入使用与具体参与设备绑定的加密会话。
- 首版不要求账号。保留通过现有已绑定设备添加新设备的流程；所有设备和密钥都丢失时无法恢复，需重新建立空间。

### 4.2 首次配对

1. 电视选择“添加手机”，创建短期配对邀请，建议有效期 5 分钟。
2. 二维码包含协议版本、服务地址、邀请 ID、一次性随机凭证及绑定发起设备公钥的信息，不直接放长期同步密钥。
3. 手机在 Cineo App 内扫码，显示服务地址和待绑定电视，提交自己的设备公钥。
4. 两端通过成熟、经过审查的协议建立配对加密通道，将双方公钥及邀请绑定到握手内容；显示一致的短验证码，用户在电视确认。不要自行拼接密码学协议。
5. 服务端原子消费邀请，建立设备授权；电视通过配对加密通道交付空间数据密钥。
6. 手机安全保存密钥和设备凭证，显示“已绑定”；两端按既定规则合并首次同步数据，不覆盖删除本地数据。

邀请到期、取消或完成后不能再次兑换；需要限制猜测和重复申请次数。二维码过期通过服务端拒绝兑换实现，不能仅靠界面倒计时。用户主动截图或系统截屏仍可能泄露配对材料，应尽量减少展示并在适用平台保护敏感窗口。

首次使用由电视创建空间；以后任何获准的已绑定设备都可发起添加。若两台设备已有不同空间，首版提示选择空间，不自动合并两个空间。

### 4.3 解绑与恢复

- 设备页提供设备名称、最近活动时间和解除绑定；凭证撤销后立即拒绝新请求并断开相关实时连接。
- 撤销访问无法收回设备已经解密或缓存的旧数据。
- 若要求被移除设备不能解密未来数据，需轮换空间数据密钥。给其余设备分别用其公钥封装新密钥，允许它们稍后上线领取，无需同时在线。
- 首版必须明确实现凭证撤销；密钥轮换协议在上线前定稿，不把“移除设备”描述成能擦除对方既有数据。
- 不允许只凭客户端提交的 `space_id` 加入空间，也不将空间数据密钥直接当服务端访问 Token。

## 5. 手机输入流程

### 5.1 电视发起

1. 搜索、TMDB Token、站点地址等字段旁提供“手机输入”。
2. 点击后收起软键盘，创建输入会话并显示待输入字段、允许的设备和剩余有效时间。
3. 已绑定手机在 App 的“我的电视”中选择该电视并获取当前待输入会话；未绑定时先走扫码配对。
4. 手机粘贴后点击“发送”；电视校验会话和字段后更新本地状态。
5. 电视返回应用结果，手机随后显示“已填入”。会话完成后关闭或重新生成，避免重复提交。

首版采用用户打开手机 App 主动查看的方式，不依赖手机后台常驻连接或系统推送。App 也可以先进入设备页，但电视未开启输入会话时不能直接覆盖字段。

### 5.2 会话协议

每条指令绑定 `message_id`、发送/接收设备、`session_id`、`field_id`、字段版本和有效期。服务端校验授权与路由，电视再次校验接收条件。

- 默认输入会话建议 2 分钟有效，输入面板建议最长 5 分钟自动退出。
- 指令短时有效，建议不超过 30 秒；不向离线电视持久排队。重连后重新获取会话。
- 输入长度由字段限制，例如搜索词 200 字符、地址 4 KB、Token 8 KB；以上为待验证建议值，服务端还需统一字节上限。
- 同一 `message_id` 重试只能应用一次；旧会话、旧字段版本和重复指令不能覆盖后来编辑。
- 电视离开页面、关闭弹窗、切换字段或解绑，立即终止原会话。
- 服务端“已接收”和电视“已填入”分开；超时没有回执时显示“未确认”，不能假报成功。

### 5.3 字段行为

| 字段 | 收到后的动作 |
|---|---|
| 搜索词 | 填入，可由用户明确选择“填入并搜索” |
| TMDB Token | 填入后沿用现有验证与保存流程，手机不回显电视原有 Token |
| 站点地址/名称 | 填入编辑表单，按已有规则验证和保存 |

首版使用“粘贴后提交”，不做逐字符镜像。手机不自动读取剪贴板。敏感输入不进入持久消息队列、分析事件或日志，内存缓冲在确认/超时后释放；服务异常时也不持久补投。

## 6. 持久同步与原方案的关系

继续采用 [SYNC_DESIGN.md](./SYNC_DESIGN.md) 的本地优先、outbox、站点跨端键、按集进度、白名单设置、墓碑和重新解析播放 URL 等方向。两端本地迁移仍按原文拆分，不能直接用本地 `source.id` 匹配站点。

服务端每个 `(space_id, entity, key)` 只保留最新状态，分配空间内单调递增 `seq`，并建立按空间与序号查询的索引。序号用于增量游标，不表示永久保存所有旧版本。需要支持重试幂等、分页与写入并发下的最终收敛，验证分页过程中同一记录再次更新仍不会永久漏同步。

### 6.1 删除、保留与全量重建

- 墓碑建议保留 90 天。历史超过条数/保留期的清理也是同步变更，不能本地静默删除后又被另一端恢复。
- 游标超出保留窗口时，返回 `resync_required`。
- 重建时先取得服务器有效快照及保留边界，再按明确规则重放仍有效的本地待上传操作；不能把陈旧设备的全库无条件重新上传，否则已清理的墓碑会导致旧数据复活。
- 具体采用空间/实体代际或重建基线规则，需在协议阶段确定。首版不允许以“上传全部旧数据”代替该规则。

### 6.2 冲突

原草案的时间戳 LWW 可作为起点，但必须统一服务端和客户端的比较规则，包含删除及平局规则。不能只在服务端截断超前时间，而让客户端继续使用原始时间比较。设备时钟偏移、离线并发和旧记录恢复需用协议用例验证。

## 7. 降低请求量与连接成本

下列策略替换原草案“每 30 秒推送”的默认安排。

| 场景 | 建议策略 |
|---|---|
| 本地修改 | 事务内写 outbox，同键合并；没有脏数据不推送 |
| 收藏、站点、共享设置 | 短暂防抖后批量上传，不逐次拉全量 |
| 播放中 | 本地保持现有保存频率；云端每 2～5 分钟最多批量上传一次最新进度 |
| 暂停、退出播放器 | 触发一次合并上传，与进行中的请求去重 |
| 切后台 | 尽力补传，不能依赖操作系统一定允许完成；剩余 outbox 下次启动重试 |
| 拉取 | 启动、回前台、手动同步触发，合并重复触发并设置最小间隔 |
| 输入连接 | 电视打开输入面板、手机进入输入页时建立，结束/超时即断开 |
| 故障 | 指数退避加随机抖动，遵守 `Retry-After`，避免设备同时重试 |

首版不为了同步历史而让每台设备全天保持 WebSocket。后续若需要“对端修改后马上更新”，应单独评估轻量变更通知与连接费用。

## 8. 配额与清理建议

以下按同步空间计费与限额，避免一个用户绑定多台设备后重复计算同一份数据；数值需通过试运行校准。

| 项目 | 首版建议起点 |
|---|---|
| 每空间设备数 | 5 台 |
| 观看进度 | 最近 1,000 条按集记录 |
| 收藏 | 1,000 条 |
| 站点 | 100 条 |
| 密文和元数据总存储 | 20 MB，包含有效墓碑；保留清理所需余量 |
| 批量同步请求 | 最多 500 条且总请求体不超过 1 MB |
| 实时输入会话 | 每电视最多 1 个，每空间最多 2 个 |
| 请求限流 | 按 IP、设备、空间分层设置；具体速率经测量后确定 |
| 运行日志 | 默认 7～14 天，采样记录，排除正文和凭证 |
| 备份 | 明确保留份数、周期与恢复流程，禁止无限累积 |
| 长期闲置空间 | 可考虑 180 天后进入清理流程；需事先告知并提供宽限，首版是否启用待定 |

服务端只见密文，无法自行判断哪条是“最近观看”。实体淘汰主要由客户端产生删除操作；服务端可按数量、字节及可见元数据执行配额，不能随意删掉加密实体来假装完成业务清理。

超额时停止新增或返回可理解的配额错误，提示整理数据，已有本地能力继续可用。不静默丢弃待同步数据；删除与必要元数据更新需留有空间，避免超额后无法清理。

## 9. 容量与费用估算

下列是建模假设，不是实际测量或供应商报价。费用需按最终平台的存储、读写操作、出站流量、连接时长/消息数、计算、日志及备份项目分别核算。

假设每个活跃空间有 1,000 条记录，每条加密信封平均 2 KB，以十进制粗估：

| 活跃空间数 | 记录原始存储 |
|---|---|
| 1,000 | 约 2 GB |
| 10,000 | 约 20 GB |
| 100,000 | 约 200 GB |

这些数字未含索引、设备表、墓碑、备份和数据库页开销。实际应测量样本后确定放大系数，不能把原始字节直接视为账单容量。

请求量可能比存储更早产生费用：若 10,000 个活跃空间每天各有 1 台设备活跃 2 小时，每 30 秒请求一次，仅该周期请求就约 240 万次/天。每 5 分钟一次则约 24 万次/天；两者都未包含拉取、分页、重试和其他设备。不变更就不发送，可以继续降低请求量。

费用模型：

```text
月费用 ≈ 计算/请求 + 数据库存储 + 数据库读写 + 出站流量
       + 实时连接/消息 + 日志 + 备份 + 基础固定费用

峰值输入连接数 ≈ 同时开启手机输入的会话数 × 2
```

注册用户数、月活跃空间数、日活跃设备数、峰值并发需要分别统计。差异同步减少网络字节，但索引缺失导致的数据库扫描仍可能增加读取成本。

上线前记录：每空间平均字节数、日请求数、每次扫描/返回行数、上传/下载字节、输入会话时长、峰值连接数、日志与备份大小。先以小规模试运行数据估算 1 千/1 万/10 万活跃空间，不承诺固定月费。

预算设月度目标和 50%/80%/100% 告警；告警不等于自动停费保障。配合平台实际支持的硬限额及应用限流。压力下先暂停新的实时输入、拉长自动同步间隔，保留明确限额的手动同步；超出预算时可暂停云端服务并清楚提示，本地操作继续可用。

## 10. 托管与 Tailscale 的定位

若已有可维护的后端，优先复用其部署、数据库、鉴权和监控；若没有，选择能承载 HTTPS、数据库和短时双向连接的托管方案。选择前核实目标地区可达性、数据库读写计费、长连接限制、备份恢复、预算控制及数据导出能力，不在本文锁定平台或引用实时价格。

Tailscale 作为可选的自托管访问通道，例如用户把 Cineo 后端部署在 NAS，仅通过私有网络访问。它不替代同步协议，也不提供本方案所需的离线数据保管。设备即便网络互通，也仍需 Cineo 配对授权。

参考：[Tailscale 对设备互通与目标服务的说明](https://tailscale.com/docs/how-to/connect-to-devices)、[WebSocket 协议](https://www.rfc-editor.org/info/rfc6455/)。

## 11. 实施顺序与验收

### 阶段 A：协议与成本基线

- 定稿设备身份、一次性邀请、加密握手、撤销和密钥轮换。
- 定稿 sourceKey、冲突比较、墓碑清理及过期设备重建规则。
- 确认托管方式、目标地区、预算、配额、数据保留政策。
- 使用真实两端数据测量信封大小与增量查询成本。

### 阶段 B：绑定与手机输入闭环

- 实现最小后端设备授权和临时路由、TV 输入会话、Flutter 扫码和设备页。
- 先覆盖搜索、TMDB Token、站点地址；不等待完整历史同步才能交付输入功能。
- 验收：两端异网输入、重复/过期指令、页面切换、断网未确认、无权限设备、解绑后的连接失效、敏感日志检查。

### 阶段 C：持久同步

- 根据现有同步草案改造两端数据库与 outbox，增加最新状态存储、分页与清理。
- 验收：手机关闭后电视拉取、双向离线修改、删除传播、超期设备不复活旧数据、退出播放进度、服务故障下本地继续工作。

### 阶段 D：小规模运行与费用验证

- 验证限流、配额、恢复备份、客户端退避和告警。
- 以真实日活与峰值数据估算扩容成本，再决定开放规模。
- 验收：无变化时没有空推送、无输入时没有输入长连接、超额可清理、预算降级不影响本地播放。

| SYNC_DESIGN 第 11 节 | 替换固定 30 秒推送为有变化批量上传及前台按需拉取 |
| SYNC_DESIGN 第 13 节 | 加入实时输入阶段与成本验收；输入闭环可早于完整数据同步 |
| DECISIONS D-06 | 单次填写 Token 与长期共享 Token 分开决策 |
| DECISIONS D-07、D-08 | 确认分阶段范围、后端部署、预算、配额和保留策略 |

## 13. 评审需要确定的事项

1. 是否接受首版云端路径、Cineo App 扫码绑定、Tailscale 仅作可选自托管通道。
2. 是否接受“电视主动开启输入、手机提交一次”的交互，以及首版不做后台通知和逐字符镜像。
3. 后端复用还是新建、部署地区、月度预算与试运行规模。
4. 配额与历史保留策略、长期闲置数据处理方式。
5. 设备凭证撤销与密钥轮换的首版范围、账号与恢复是否后续再做。

用户评审确认后，再更新决策记录、冻结协议并开始功能开发。
